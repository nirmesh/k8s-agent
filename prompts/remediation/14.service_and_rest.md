I do NOT want to add support for one Kubernetes incident at a time.

The previous ImagePullBackOff scenario worked, but another scenario
(Service unavailable due to selector mismatch) was missed.

Do NOT solve this by adding Service-selector-specific troubleshooting
logic.

We need to generalize the SRE Investigator architecture.

GOAL

Build an agent capable of investigating previously unseen Kubernetes
incidents using generic Kubernetes discovery tools.

The Python/backend code should provide capabilities.

The LLM should determine:
- what evidence it needs
- which resources are related
- which tools to call
- whether enough evidence exists
- what the root cause is

Do NOT implement incident workflows such as:

investigate_image_pull()
investigate_service_selector()
investigate_crashloop()
investigate_oom()
investigate_pvc()
investigate_dns()

There should be NO incident-type switch statement driving investigation.

==================================================
5. INVESTIGATION LOOP
==================================================

Replace any fixed investigation sequence with a hypothesis-driven
tool loop.

The agent receives:

INCIDENT / USER GOAL

Example:

"Users cannot reach web-service in namespace sre-lab."

The agent repeatedly performs:

OBSERVE
What facts are currently known?

HYPOTHESIZE
What plausible explanations remain?

INVESTIGATE
What evidence would distinguish them?

ACT
Call ONE OR MORE appropriate read tools.

OBSERVE
Consume the results.

Repeat until:

A. root cause is sufficiently supported

B. more evidence cannot be obtained

C. investigation budget is reached


Do NOT implement this logic as incident-specific Python branches.

The LLM performs this reasoning using tool calls.


==================================================
6. INVESTIGATION SCOPE
==================================================

Start from the reported resource, namespace, symptom, or incident.

Expand outward through related resources.

Example:

        |

        +-- selectors/labels

        +-- owners

Another incident may naturally become:

        |
        +-- status
        +-- events

        +-- owner
        +-- node

Another may become:

reported Ingress
        |
        +-- backend Service
        +-- EndpointSlice
        +-- Pods

These are examples only.

DO NOT hardcode these sequences.


==================================================
7. NO_ISSUE RULE

NO_ISSUE must mean:

"The reported symptom/resource was investigated and evidence indicates
that the reported problem is not currently observable."

It must NOT mean:

"Pods and nodes look healthy."

If the agent cannot evaluate the reported symptom:

NEED_MORE_EVIDENCE

If root cause is found:

DIAGNOSED


==================================================
8. EVIDENCE-BASED DIAGNOSIS

Final diagnosis must reference actual collected evidence.

Return:

{
  "status": "DIAGNOSED | NEED_MORE_EVIDENCE | NO_ISSUE",

  "rootCause": "...",

  "confidence": 0.0,

  "affectedResources": [],

  "evidence": [],

  "investigationTrace": []
}

Do not allow a diagnosis to cite information that was not returned
by a tool or provided by the user.

The investigation trace should contain tool activity only, not hidden
chain-of-thought.

10. VERIFICATION

Do NOT hardcode:

Examples:

These are examples, NOT hardcoded incident workflows.

Verification should evaluate the planned success criteria using
generic read tools.


==================================================
11. TOOL BUDGET

Do not solve investigation failures simply by increasing max iterations.

Implement:

- same-resource repeated-read detection
- observation caching where appropriate
- bounded investigation
- final synthesis when budget is reached

If evidence is insufficient after the budget:

NEED_MORE_EVIDENCE
